Final summary

How the stop-check governs the loop

Every round the pipeline calls the Evaluator fresh against the current draft, then the Critic for qualitative issues, then the Improver to produce the next draft — each a live API call, never a canned template. After each Evaluator call, three checks run in strict order: (1) plateau — has the score improved by less than the configured delta for two consecutive rounds? (2) threshold — has the score crossed the target set at interview? (3) hard cap — a safety fallback (12 rounds) so the loop can never run forever. Whichever fires first ends the loop and hands the running history to the Final Reviewer, which never edits code itself — it only synthesizes what happened.

Extension ideas

  • Safety Monitor agentAdd a dedicated pass that screens generated code for unsafe patterns (eval, shell injection, unbounded recursion) before it ever reaches the Evaluator.
  • Memory Manager agentPersist distilled lessons ("avoid mutable default args", "prefer early returns") across separate runs, not just within one run's history.
  • Multi-file scopeExtend the Executor to plan and generate across multiple files/modules with a dependency graph instead of a single function.
  • Test-driven loopHave the Executor also generate unit tests, and let the Evaluator run them (via a sandboxed tool call) as part of the score.
  • Human-in-the-loop gateInsert an approval checkpoint before the Final Reviewer commits, so a person can veto or redirect a round.
  • Parallel draftsRun 2–3 Executors in parallel per round and let the Evaluator pick the strongest draft to improve further.
